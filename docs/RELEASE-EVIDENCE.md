# Production release and change-failure evidence

This repository records one privacy-safe JSON evidence object for each reviewed
production promotion. The record is generated by the manual
`.github/workflows/release-evidence.yml` workflow and validated by
`scripts/release-record.py`.

## Record contract

The record schema is `belacca.release-record.v1`. It contains only:

- the full source Git SHA and its derived `sha-<SHA>` release tag;
- four exact `ghcr.io/macel94/cloudnativepong-<component>@sha256:<digest>` image
  references, with one attestation state per component;
- deployment revision, Flux source revision, and Flux Kustomization revision;
- aggregate synthetic status and RFC3339 start/completion/duration timing;
- rollback status, reviewed action, detection time, recovery time, and elapsed
  timing when a rollback was completed; and
- DORA measurements for an explicitly stated window.

The validator rejects mutable tags, missing components, unbounded revisions,
private-data-shaped fields (including tokens, URLs, IPs, names, rooms, and
request bodies), inconsistent timestamps, and inconsistent DORA arithmetic.
Successful records require all four attestations to be verified. The record
explicitly declares `contains_secrets: false` and `contains_user_data: false`.
No record is checked in with live production values; the workflow uploads it as
short-lived GitHub Actions evidence after an operator supplies the observed
values.

The synthetic runner writes `synthetic-evidence.json` when
`SYNTHETIC_EVIDENCE_FILE` is set. It contains only `passed`/`failed`, start and
completion timestamps, and duration milliseconds. A missing file is a workflow
failure. The journey itself checks the homepage, health endpoint, room create,
join contract, both player WebSockets, playing state, and cleanup.

## Promotion gate and failed journey

The evidence workflow is manual-only and only runs from `main`. Before the
journey it:

1. checks the source SHA exists in repository history;
2. rejects anything other than four exact GHCR digest references;
3. verifies every GitHub Artifact Attestation against this repository and the
   pinned publish workflow; and
4. runs the post-deploy synthetic journey.

A failed journey produces a `halted` record with `pending_review` rollback
status and detection timing, then fails the workflow. It cannot be reported as
a successful promotion. The workflow does not call `kubectl`, mutate Flux, or
perform a production rollback.

If a reviewed rollback was completed, rerun the evidence workflow with
`rollback_status=completed`, the reviewed Git/Flux action, detection timestamp,
and recovery timestamp. The validator calculates and checks detection and
recovery timing. A completed rollback is represented as `rolled_back`; a
successful promotion must have `not_required` rollback status and a passed
synthetic result.

## DORA measurements

The record uses the following explicit definitions:

| Measure | Definition in this repository |
| --- | --- |
| Deployment frequency | `deployment_count / window_days`, counting production promotions in the stated UTC window. |
| Lead time for change | Seconds from the source commit timestamp to the observed promotion start. |
| Change failure rate | `failed_deployment_count / deployment_count`; failed means halted or rolled back because the post-deploy gate did not pass. |
| Recovery time | Seconds from synthetic failure/rollback detection to verified recovery after the reviewed Git/Flux action. |

Counts and timestamps are operator-supplied observations and are checked for
non-negative values, valid windows, and arithmetic consistency. A zero-count
window has frequency and failure rate zero; it must not be presented as a
production availability claim.

## Rollback boundary

Production rollback remains a reviewed Git/Flux action:

1. preserve the failed release record and synthetic evidence;
2. inspect the immutable prior release in Git history and confirm its image
   digests and attestation status;
3. submit/review a Git revert or an equivalent reviewed change restoring the
   prior immutable overlay references;
4. wait for Flux source and Kustomization reconciliation;
5. record the detection timestamp, the reviewed change, Flux revisions, and the
   first verified recovery timestamp; and
6. rerun the synthetic journey and generate the completed rollback evidence.

Do not use `kubectl set image`, `kubectl rollout undo`, or a mutable tag as a
permanent production rollback. `kubectl rollout undo` exists only in the
negative disposable rollout test and is guarded to an exact
`k3d-negative-rollout-<numeric-run-id>` context.

The exact disposable negative path is `.github/workflows/negative-rollout.yml`.
It injects a missing local image, asserts that rollout fails, times detection,
undoes only the disposable rollout, waits for recovery, and uploads aggregate
JSON evidence. It never uses a production kubeconfig or public endpoint.

## Validation commands

```bash
./scripts/release-record.test.sh
./scripts/validate-release.test.sh
npm ci --ignore-scripts
npm run test:synthetic
```

Production Flux revisions and deployment revisions cannot be observed from this
clean worktree. The evidence workflow intentionally requires an operator to
supply those values after reviewing the production cluster and refuses to fake
or infer them.
